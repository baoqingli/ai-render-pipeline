# CAD 到空间效果图流水线 — 可实施版方案（V2）

> 需求源头见 [requirement.md](./requirement.md)。
> 本版本基于对初版方案（见 [cad-to-render-pipeline.md](./cad-to-render-pipeline.md)）的评审反馈调整而来，
> 核心变化：**降低"自动解析 CAD"的预期，补齐白模、门窗洞口、视角、AI 一致性、全自动兜底（默认值 + 内部工具）等环节。**

评审确认的关键判断：

- 不要幻想 CAD 全自动解析一开始就能通吃所有图纸
- 白模必须处理门窗洞口，不能只挤墙
- AI 渲染一致性要靠模板、Seed、参考图权重控制
- MVP 不应该一上来做自动质检
- Blender 应该 headless + 队列化部署

## 目标定义

做一个 **"CAD 平面图 + 层高 + 风格描述 / 参考图 → 批量生成空间效果图"** 的工作流产品。

核心原则：

| 原则 | 保障手段 |
| --- | --- |
| **结构准确性** | 由 CAD / 白模 / 深度图保证 |
| **视觉风格** | 由 AI 渲染保证 |
| **用户兜底** | 只在结果层兜底：不满意 → 改文字描述 / 换参考图重新生成；流程内不设确认环节，CAD 不规范由默认值 + 规则兜底 |

---

## 推荐总流程

```
DXF / DWG
  ↓
DWG 转 DXF
  ↓
CAD 预处理与图层识别
  ↓
自动识别墙体 / 门窗 / 层高（低置信度用默认值兜底，不打扰用户）
  ↓
生成结构化空间数据
  ↓
Blender 自动建白模
  ↓
墙体挤出 + 门窗挖洞 + 家具体块
  ↓
生成 Depth / Lineart / Normal / 白模图
  ↓
ComfyUI / SDXL / ControlNet / IP-Adapter 渲染
  ↓
用户挑选 / 收藏 / 打分 / 重生成（改描述 / 换参考图）
  ↓
输出多套效果图
```

---

## MVP 定义：用户主流程全自动

**用户只负责输入和看结果**：输入层提供 DXF（必须）+ 文字描述 / 参考图（可选），
上传后全自动直接出图，**主流程无任何确认环节**；
不满意就修改描述 / 换参考图重新生成（结果层反馈闭环）。

> 工程判断：CAD 自动解析不可能一步通吃。解法**不是让用户中途确认**，
> 而是**默认值 + 规则兜底 + 置信度分级**——解析失败的部分按默认值出图，
> 自动解析率的提升留给 Phase 3。原"半自动操作"（选图层、框门窗、填层高）
> 降级为**内部工具**，用于解析失败户型的排查和兜底，不进产品主流程。

### MVP 输入

- DXF 文件
- 文字描述（自然语言，LLM 提取风格参数）
- 可选参考图

### MVP 输出

- 每个房间 2-4 个视角
- 每个视角 3-6 张 AI 效果图
- 支持收藏、重生成、下载

## 模块设计

### 1. CAD 输入模块

**支持优先级：**

| 格式 | 策略 |
| --- | --- |
| DXF | 直接解析 |
| DWG | 先转换 DXF |
| PDF / 图片 | 暂不作为主流程，只做后续扩展。矢量 PDF（CAD 导出）可转 DXF（有损）；扫描 / 截图 / 照片需独立识别流水线（CV + OCR），准确率概率性 |

**技术选型：**

- `ezdxf`：读取 DXF
- ODA File Converter：DWG 转 DXF
- `shapely`：几何计算
- `networkx`：线段拓扑关系
- 层高标注：DXF 内 TEXT / MTEXT 是类型化实体，直接读取（无需 OCR）；OCR 仅用于图片扩展路径

**关键限制（必须写进产品规范）：**

- 墙体建议放在 `WALL` 图层
- 门窗建议放在 `DOOR` / `WINDOW` 图层，或使用标准 Block
- 图纸单位必须明确，毫米 / 米二选一
- 墙线应尽量闭合
- **天正（TARCH）图纸必须预处理**：国内大量图纸的墙体门窗是天正自定义实体，
  导出 DXF 后为 proxy entity，语义不可读。要求导出前"天正另存为 / 分解"；
  系统必须检测 proxy 实体并提示重新导出，否则真实图纸会直接卡死解析
- 层高优先从图纸标注自动提取，缺失用默认值（2800mm）兜底，不向用户提问

### 2. CAD 清洗模块

**处理内容：**

- 删除尺寸标注、文字、轴网
- 合并短断线
- 删除重复线
- 统一单位
- 修复小间隙
- 识别墙体厚度
- 提取闭合空间区域

不要追求万能算法，应该有兜底：

```
自动识别成功 → 直接进入建模
自动识别失败 → 默认值兜底（墙厚 200 等）+ 标记低置信度，用内部工具修正，不打扰用户
```

### 3. 结构化数据模块

CAD 解析后，不要直接喂给 Blender，先转成**中间数据结构**：

```json
{
  "unit": "mm",
  "floor_height": 2800,
  "wall_thickness": 200,
  "walls": [
    {
      "id": "wall_001",
      "polygon": [[0, 0], [5000, 0], [5000, 200], [0, 200]]
    }
  ],
  "doors": [
    {
      "id": "door_001",
      "position": [1200, 0],
      "width": 900,
      "height": 2100,
      "wall_id": "wall_001"
    }
  ],
  "windows": [
    {
      "id": "window_001",
      "position": [3200, 0],
      "width": 1500,
      "height": 1200,
      "sill_height": 900,
      "wall_id": "wall_001"
    }
  ],
  "furniture": [
    {
      "id": "sofa_001",
      "type": "sofa",
      "position": [2500, 3500],
      "size": [2200, 900, 800],
      "rotation": 0,
      "source": "cad"
    }
  ],
  "rooms": [
    {
      "id": "living_room",
      "name": "客厅",
      "polygon": [[0, 0], [5000, 0], [5000, 4000], [0, 4000]]
    }
  ]
}
```

`furniture.source` 标记布局来源（`cad` = 图纸布置图元提取，`ai_supplement` = AI 补全），
供校验和缓存区分两条路径。

这个中间层很重要：后面无论接 Blender、SketchUp 还是 Web 3D，都可以复用。

### 4. Blender 白模模块

用 Blender Python API，后台运行：

```bash
blender --background --python generate_scene.py
```

**白模必须包含：**

- 墙体挤出
- 门洞挖空
- 窗洞挖空
- 地面
- 天花或开放顶部
- 简单门窗框
- 简单家具体块
- 相机
- 灯光

**关键点：**

- 门窗用 Boolean 或直接生成分段墙体
- 家具先不用精细模型，用长方体占位即可
- 家具布局两条路径：CAD 有布置 → 按布置图元放体块（`source=cad`）；
  无布置 → AI 补全布局（体块级，受房间 polygon 约束，`source=ai_supplement`），
  补全结果同样进入控制图
- AI 补全的布局必须过**确定性规则校验**：体块不重叠、不穿墙、不堵门窗洞口、
  留动线间距；校验不过就重新生成布局，不放行不合理布局
- 每个房间生成独立相机视角
- 输出深度图、线稿图、法线图、白模图

### 5. 视角生成模块

**不要随机放相机。** 规则：

- 先计算房间 polygon 的中心点
- 相机高度：`1.4m - 1.6m`
- 相机离墙至少 `0.5m`
- 视线方向朝向房间中心或开阔区域
- 用 raycasting 检查是否被墙 / 家具挡住
- 每个房间保留评分最高的 2-4 个机位

**视角评分维度：**

- 可见墙面面积
- 可见地面面积
- 遮挡比例
- 是否能看到主要家具
- 是否有门窗特征

### 6. AI 渲染模块

推荐用 **ComfyUI** 做后端工作流。

**基础组合：**

```
SDXL / FLUX
+ ControlNet Depth
+ ControlNet Lineart / Canny
+ IP-Adapter
+ Prompt 模板
+ 固定 Seed
```

**用户输入用自然语言，不用表单作为必经入口**（表单会抬高使用门槛）。
在用户和渲染 prompt 之间加一层 **LLM 提取**：

```
用户自然语言描述（"温馨日式原木风，暖光"）
  ↓ LLM 结构化提取（Schema 约束，缺省字段取默认值）
风格参数 JSON
  ↓ 确定性模板拼装（不是 LLM 直接写渲染 prompt）
稳定 prompt（正面 + 负面）
```

风格参数体系（LLM 提取的目标 Schema；仅供内部诊断与调试，不作为用户输入表单）：

| 维度 | 选项 |
| --- | --- |
| 风格 | 现代简约 / 奶油风 / 原木风 / 法式 / 侘寂 / 轻奢 |
| 地面 | 木地板 / 微水泥 / 大理石 / 地砖 |
| 墙面 | 白墙 / 艺术漆 / 木饰面 / 石材 |
| 光照 | 暖光 / 自然光 / 无主灯 / 冷光 |
| 预算感 | 经济 / 中档 / 高端 |

要点：

- LLM 只负责"自然语言 → 参数"，受枚举校验约束；最终 prompt 由确定性代码拼装，保证批量一致性
- 不设参数确认环节：对结果不满意 → 追加 / 修改描述或换参考图 → 重新生成
- 无法识别的风格意图按默认值出图，由用户下一轮描述覆盖，不弹窗询问

**正面提示词示例：**

```
modern minimalist interior design, warm wood flooring,
white walls, soft indirect lighting, clean furniture,
realistic architectural visualization, high quality render
```

**负面提示词：**

```
distorted wall, warped geometry, extra window, extra door,
broken perspective, floating furniture, cluttered layout
```

**一致性控制：**

- 同一项目固定 Seed 范围
- 同一风格模板固定基础 prompt
- 参考图使用 IP-Adapter，权重建议 `0.6 - 0.8`
- 同一房间多视角共享材质描述
- 同一项目保存风格配置，可复用到所有房间

**多模型支持（可选模型列表）：**

渲染引擎抽象为两类，渲染任务带 `model_id`，用户可选（默认本地引擎）：

| 引擎类型 | 模型 | 结构控制方式 | 特点 |
| --- | --- | --- | --- |
| 本地 ComfyUI | SDXL / FLUX + ControlNet | Depth / Lineart 控制图 | 开源、无按张边际成本、结构控制强 |
| 远程 API | Gemini 图像系（Nano Banana / 香蕉 1、香蕉 2）、GPT Image（OpenAI）、Seedream（字节 / 火山引擎）等 | 白模图 / 线稿 / 深度图作为图生图或编辑参考输入 | 效果上限高、结构保持式编辑能力强（尤其 Gemini 系）、闭源按张付费、无 ControlNet 接口 |

约束与注意：

- 任何接入的模型必须有**结构控制机制**（ControlNet 或图生图 / 编辑参考），
  否则违背"结构由白模保证"的第一原则
- API 模型的结构保持是概率性的，接入前用同一组控制图实测对比再决定默认参数
- 竞品对标：酷家乐的模型选择是**聚合第三方顶级模型**，无独占壁垒——
  "香蕉 1 / 香蕉 2" = Google Nano Banana 系（Gemini 图像模型）、
  "Image 2.0" = OpenAI GPT Image、Seedream = 字节系，全部可通过对应 API 接入；
  ComfyUI 已有 Google 官方 partner 节点，API 模型可统一纳入 ComfyUI 工作流编排

**引擎接入的编排架构（统一接口，不写两套流程）：**

API 模型进 ComfyUI 有三种方式：官方 partner 节点（如 Google Nano Banana Pro）、
社区节点（GPT Image / Seedream 均有）、自写 HTTP API 节点（约百行代码）。
但生产编排建议**引擎接口抽象**：

```
渲染任务（model_id + 控制图 + prompt + 参数）
  ↓
RenderEngine 接口（submit → results）
  ├─ ComfyEngine     → 本地 ComfyUI 工作流（SDXL / FLUX + ControlNet）
  └─ DirectAPIEngine → 直连 Gemini / OpenAI / 火山引擎 SDK
```

分阶段策略：

- **Phase 1（实验期）**：全部走 ComfyUI 工作流（API 模型用节点接入），
  一套测试框架完成所有引擎的 A/B 对比，迭代最快
- **生产期**：API 模型切到直连 SDK 实现——计费计量、按用户限流、重试 / 超时、
  Key 轮换是业务必需，放在节点里不透明且难运维；同时避免 API 等待
  （单张 10-60 秒）占用 ComfyUI worker 执行槽位拖慢本地渲染队列
- 上游（任务队列 / 缓存 / 结果筛选 / 增量重生成）只认 RenderEngine 接口，
  两种实现对上游无感，切换零成本

### 7. 结果筛选模块

MVP 不建议做复杂自动质检。

**第一阶段做：**

- 用户收藏
- 用户打分
- 用户重生成
- 用户选择某张图继续变体生成

**可以加的简单自动过滤：**

- CLIP 判断图像是否符合 prompt
- 图像清晰度检测
- 黑图 / 空图检测
- 分辨率和主体区域检测

复杂的"墙线是否偏移"放到后期。

### 8. 增量重生成与缓存模块

反馈闭环（改描述 / 换参考图 → 重新生成）是**高频操作**，
不能每轮都全链路重跑。按用户改动的范围决定重算层级：

| 用户改动 | 重算范围 | 复用内容 |
| --- | --- | --- |
| 更换 CAD 文件 | 全链路 | 无 |
| 修改文字描述（风格意图） | 仅 AI 渲染 | 结构 JSON、白模、Depth / Lineart 控制图、相机 |
| 更换 / 新增参考图 | 仅 AI 渲染（IP-Adapter 分支） | 控制图、prompt 模板、Seed 策略 |
| 单张结果不满意 | 单个视角 × 单风格变体 | 其余全部结果 |

实现要点：

- **缓存键分层**，每阶段产物落对象存储，key 可复算：
  - 结构 JSON key = hash(DXF 内容 + 解析规则版本 + 默认参数)
  - 白模 / 控制图 key = hash(结构 JSON + Blender 脚本版本 + 相机参数)
  - 渲染结果 key = hash(控制图 key + 风格参数 JSON + 参考图 hash + 模型 ID + Seed + 工作流版本)
- **版本号进缓存键**：解析规则、Blender 脚本、ComfyUI 工作流升级后，
  旧缓存自动失效，不会读到过期产物
- **AI 补全布局不依赖风格参数**：家具布局只由房间几何 + 功能类型决定（进白模 key），
  风格差异（经济 / 高端等）由渲染层的 prompt 和材质体现，不由布局层体现——
  否则"改描述仅重渲染"的复用规则会被打破
- **渲染任务粒度 = 视角 × 风格变体**：支持"重跑某一张"，
  与 MVP 输出的收藏 / 重生成对齐
- 典型迭代轮次（只改描述 / 参考图）跳过解析和白模，直接从缓存的控制图进
  ComfyUI，迭代延迟从"全链路分钟级"降到"渲染级"

## 技术可行性评估

**结论：架构各层均为生产验证过的技术（ezdxf / Blender headless / ComfyUI /
ControlNet 均有商业先例），没有需要发明尚不存在技术的地方。**
风险集中在边界，不在原理：

| 环节 | 可行性 | 说明 |
| --- | --- | --- |
| DXF 解析 / 实体读取 | ✅ 成熟 | 标注、文字是类型化实体，删除 / 提取是确定性操作 |
| 双线墙识别 / 中心线重建 | ⚠️ 困难但可行 | 交叉、洞口处易错，准确率随图纸规范度变化，默认值兜底 |
| 天正自定义实体 | ⛔ 不可直接解析 | 必须要求导出前分解；检测到 proxy 实体提示重新导出 |
| Blender headless 白模 | ✅ 成熟 | Boolean 对退化几何脆弱，**主路线用分段墙体**（分析式开洞） |
| 视角生成 / raycasting | ✅ 成熟 | 标准 API |
| SDXL + ControlNet 渲染 | ✅ 成熟（概率性） | 室内效果图标配架构；结构保持是概率性的，不是确定性的 |
| 多视角材质一致性 | ⚠️ 已知难题 | 共享描述 + 固定种子可缓解不能消除；独立成图场景可接受 |
| ComfyUI 并发 | ✅ 需工程处理 | 单实例会话级排队，并发靠多实例 / 每 GPU 一个 worker |
| 缓存 / 队列 / 服务拆分 | ✅ 标准工程 | 无特殊风险 |

两条必须提前校准的预期：

1. **"结构 100% 不变形"做不到**：控制图权重高 → 贴近白模但呆板；权重低 → 结构漂移
   （多一扇窗、墙微弯）。工程口径：批量生成 + 自动过滤 + 挑优交付，达到**目视结构
   一致**，不承诺逐像素一致。这正是 Phase 1 要实测确定参数区间的原因。
2. **渲染质量上限需要 Phase 1 实证**：架构可行性 ≠ 效果达标，风格化质量是否达到
   业务要求只有跑出来才知道。Phase 1 的 3-5 天是全方案风险最高、最该先做的一步。

工期口径：Phase 2 的"2 周"指**一个标准演示户型调通**；真实客户图纸（天正、乱图层、
不规范命名）的鲁棒性归 Phase 3。算力量级：5 房间 × 3 视角 × 4 变体 ≈ 60 张 SDXL
生成，单卡约 10-20 分钟 / 项目，可接受。

## 开发路线图

### Phase 1：验证 AI 渲染效果（3-5 天）

**先跳过 CAD。**

输入：

- 人工准备的白模图
- 深度图
- 线稿图
- 参考图
- 风格 prompt

目标：

- 跑通 ComfyUI API
- 测试 Depth + Lineart 的控制效果
- 找到稳定参数
- 确认生成图质量能不能达到业务要求

交付：

- 一个可调用的 AI 渲染接口
- 3-5 套风格模板
- 每套模板可批量生成多张图

### Phase 2：CAD 到白模自动链路（2 周左右）

输入 DXF，主流程全自动。

能力：

- 内部诊断视图：显示 CAD 线稿与自动识别结果，供排查解析失败（不给终端用户）
- 规则自动识别墙体图层（图层名 / 线宽 / 闭合性），失败用默认墙厚
- 规则自动识别门窗（块名 / 图层），失败按无洞口处理并标记
- 层高从标注自动提取，缺失用默认值 2800mm
- 后端生成结构 JSON
- Blender 生成白模、深度图、线稿图
- 接入 Phase 1 的 AI 渲染

交付：

- DXF → 白模 → 效果图全自动链路（用户无中途交互）
- 支持一个标准户型跑通
- 增量重生成：改文字描述 / 换参考图时复用缓存控制图，只重跑渲染阶段
- 半自动修正工具（选图层 / 框门窗 / 改层高）作为内部工具，兜底解析失败的户型

### Phase 3：规则化自动解析（1-2 个月）

能力：

- 自动识别 `WALL` 图层
- 自动识别门窗 Block
- 自动提取 Block 名里的尺寸，例如 `Door_900`
- 自动识别房间区域
- 自动生成多个房间视角
- 解析失败时自动降级兜底（默认值 / 跳过），不阻塞不出错，并记录待改进样本

交付：

- 规范 DXF 下的自动批量生成（低置信度自动降级兜底，用户无感）
- 多房间、多视角、多风格批量出图

### Phase 4：产品化增强

能力：

- 项目管理
- 风格库
- 材质库
- 历史版本
- 用户打分训练偏好
- 企业制图规范模板
- 渲染队列和并发控制
- 缓存与增量重生成策略完善（按缓存键自动失效、缓存命中率与成本看板）
- 成本统计

## 推荐技术栈

### 后端

- Python（PSF）
- FastAPI（MIT）
- Celery（BSD）/ RQ（MIT）
- Valkey（BSD，Redis 的开源分支；Redis 自 2024 年起为 RSAL/SSPL，非 OSI 开源）
- PostgreSQL（PostgreSQL License）
- MinIO（AGPLv3，内部自用合规；回避 AGPL 可换 SeaweedFS，Apache 2.0）

### CAD / 几何

- ezdxf（MIT）
- shapely（BSD）
- networkx（BSD）
- DWG 转 DXF：ODA File Converter（**选定方案**：免费、转换成功率高；闭源但为
  独立进程调用，零代码耦合。开源备选 LibreDWG（GPL）仅作许可条款变化时的退路）
- Blender Python API（GPLv3+；subprocess 调 `--background --python`，不传染自有代码）

### AI

- 风格参数提取 LLM：**Phase 1 起用智谱 GLM API**（OpenAI 兼容端点，免自建 vLLM，
  GPU 专供 ComfyUI）；自部署开源模型（Qwen / DeepSeek，vLLM）为切换项，
  接口不变（OpenAI 兼容 base_url 可配置）
- ComfyUI（GPLv3）
- SDXL（Open RAIL++-M，允许商用）
- FLUX（dev 版权重许可限制商用，采用前核对当前条款）
- ControlNet Depth / Lineart / Canny（OpenRAIL / Apache）
- IP-Adapter（Apache 2.0）
- CLIP（open_clip，Apache 2.0）

### 前端

- React（MIT）/ Vue（MIT）
- Three.js（MIT）
- SVG / Canvas CAD 预览（内部诊断视图）
- 图层选择 / 房间墙体门窗修正 UI（内部兜底工具，不进用户主流程）
- 图片瀑布流 + 收藏 + 评分（用户结果层）

### 部署

- Blender 独立 Worker
- ComfyUI 独立 GPU Worker
- FastAPI 只负责业务接口
- Redis 管任务队列
- 文件统一进对象存储
- Blender 用 headless 模式
- **不要在 Web 服务进程里直接跑 Blender**

**开源结论：除 DWG 转换使用免费闭源的 ODA（独立进程调用，零代码耦合）外，
其余全链路均为开源**——自部署 Qwen 替闭源 LLM API、Valkey 替 Redis、SDXL 替
FLUX。闭源组件均为进程 / API 级调用，许可条款变化时随时可替换
（DWG 转换的退路为 LibreDWG）。

## 最终结论

初版方案方向正确，但需要：

1. 降低"自动解析 CAD"的预期
2. 补齐白模、门窗洞口、视角、AI 一致性、人工兜底这些环节

优化后的可落地路线：

```
先验证 AI 渲染质量
  → 再做自动 CAD → 白模（默认值兜底）
  → 最后逐步增强自动解析能力
```

这比一开始就做"上传任意 CAD 自动出图"靠谱得多，也更适合团队分阶段交付。
